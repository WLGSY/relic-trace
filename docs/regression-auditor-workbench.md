## 二、已知问题验证与处理

### K1 最近操作显示英文方法名（系统管理员、录制员、审核员均存在）

**现象复现**

1. 以任一角色登录后台，进入「系统工作台」
2. 查看右侧「最近操作」
3. 记录显示 `Auth · logout`、`Relic · deleteAttachment`、`Relic · uploadAttachment`，内容为「张录入 执行了 deleteAttachment」

**根因**：`OperateLogAspect` 直接把控制器类名去后缀当模块名、把 Java 方法名当操作类型落库，未做任何中文化；「操作日志」页的类型下拉却是中文（新增/修改/删除/审核/提交/登录/导出），因此日志永远筛不出来。

**处理（已修复）**

- 新增 `common/.../OperateLogDict.java`：控制器 → 模块中文名（登录认证 / 藏品档案 / 藏品征集 / 业务审核 / 修复管理 / 展览借调 / 注销管理 / 库房管理 / 系统管理），方法 → 操作类型 + 操作描述（如 `uploadAttachment` → 上传 / 上传藏品影像），并支持「模块:方法」细化（`Collection:create` → 新增征集申请）；未登记方法退化为「操作」，不再出现英文
- `OperateLogAspect` 改为经字典写入，内容格式统一为「操作人 + 中文动作」
- 历史 36 条记录用 SQL 回填（模块、类型、内容三列同步修正）
- `LogView.vue` 的操作类型筛选项补齐「上传 / 重建 / 处理 / 退出」

**验证**：全量 100 条日志扫描，含英文的模块/类型/内容记录数 = **0**；工作台显示「业务审核 · 审核 | 李审核 审核单据」。

### K2 馆藏概览全部显示 0 件

**现象复现**

1. 以审核员登录，进入「系统工作台」
2. 页面底部「馆藏概览」六项（IN STOCK / OUT / ON LOAN / IN REPAIR / CANCELLED / SCANS）全部为 `0 件`
3. 同期数据库实有 13 件藏品、11 件在库、1 件出库、1 件修复中、累计扫码 16 次

**根因**：`StatsServiceImpl.getOverview()` 只返回 `totalRelics / totalWarehouses / totalCategories / totalUsers / totalStocks / totalCollections` 六个字段，而前端绑定的是 `inStock / outbound / loaned / repairing / cancelled / scanTotal / publicCount / monthNew / monthStock / monthTrace / pendingAudits`，字段全部取不到 → `?? 0` 兜底成 0。这不是"没数据"，是接口契约与前端不匹配。

**处理（已修复）**

- `getOverview()` 补齐全部指标：五个库存状态分组计数、公开藏品数、本月新增、本月出入库次数、本月溯源条数、累计扫码、待审核合计（五类业务口径与审核工作台一致）
- 保留原六个基础字段，`StatsView` 不受影响
- 新增 `countByStockStatus()` 私有方法复用分组统计

**验证**：审核前接口返回 `总数13 在库11 出库1 借出0 修复中1 已注销0 公开13 扫码16`，与 `SELECT stock_status, COUNT(*)` 结果逐项一致；审核动作完成后变为 `在库8 出库2 借出1 修复中2 已注销2`，分布合计 = 总数 15。

## 三、新发现的异常（按严重程度排序）

### N1【严重】审核工作台「审核」与「批量通过」在页面上必然失败

**涉及角色**：审核员（系统管理员同路径）

**复现步骤**

1. 以张录入登录，新建一条修复申请使其进入待审
2. 以李审核登录，进入「审核工作台」，点击任意待办行的「审核」，填意见后提交
3. 页面提示「系统繁忙，请稍后重试」；点「批量通过」同样失败

**根因**：前端 `AuditDialog.vue`、`AuditView.vue` 提交的字段是 `bizId`（与待办列表返回字段一致），后端 `AuditDTO` 只有 `fkBizId`、`batchAudit` 也只读 `fkBizId`，取不到 id 后抛出「审核对象不完整」。接口直连传 `fkBizId` 才能成功，因此此前接口测试未暴露。

**处理（已修复）**：`AuditDTO` 增加 `bizId` 别名并重写 `getFkBizId()` 做归一；`batchAudit` 同时兼容 `fkBizId` / `bizId`，并兼容 `bizType` 为字符串的入参。

**验证**：仅传 `bizId`（模拟页面）单条审核返回 200，单据状态正确流转；批量通过 2 条返回「批量审核完成」，待办归零。

### N2【中】审核工作台顶部五类卡片筛选失效

**复现步骤**：审核工作台有 5 条不同类型的待办 → 点击「修复审核」卡片 → 列表仍显示全部 5 条（预期只剩修复 1 条）。

**根因**：`GET /audits/pending` 只接收 `PageQuery`（pageNum/pageSize/keyword），前端传的 `bizType` 被直接丢弃，服务层汇总五类后未做过滤。

**处理（已修复）**：新增 `AuditQuery extends PageQuery`（增加 `bizType`），控制器改绑该类，服务层按类型过滤后再分页。验证：`bizType=1..5` 各命中 1 条，全量 5 条。

### N3【严重】修复申请永远进不了待审核，修复审核模块空转

**复现步骤**：录入员在「修复管理」新建一条修复申请 → 审核员待办中始终看不到 → 修复审核卡片恒为 0。

**根因**：`RepairServiceImpl.create()` 默认 `apply_status=0`（草稿），而系统没有"提交修复申请"的接口与按钮，审核侧只认 `apply_status=1`，单据被永久卡在草稿。

**处理（已修复）**：创建即置为 1（待审核），与借调/注销"新建即待审"的口径一致，并在注释中说明原因。

### N4【严重】修复 / 借调 / 注销 / 出入库单号无人生成，页面新增直接 500

**复现步骤**：在「修复管理」「展览借调」「注销管理」「出入库管理」分别新建单据（表单无单号输入项）→ 均返回「系统繁忙」。

**根因**：四张表的 `apply_code / loan_code / record_code` 是 `NOT NULL UNIQUE`，但服务层只做 insert，不生成单号，前端也不填；此前只有征集单补过自动编号，其余四类漏改。

**处理（已修复）**：四个 Mapper 增加原生 `MAX(...)` 查询（绕过逻辑删除，避免与已删记录撞号），新增通用 `BizCodeUtils.nextCode()`，服务层按类型生成：修复 `XF-yyyy-NNN`、借调 `JD-yyyy-NNN`、注销 `ZX-yyyy-NNN`、出入库按业务类型 `RK-/CK-/YK-yyyy-NNN`。

**验证**：连续创建得到 `XF-2026-001`、`JD-2026-001`、`ZX-2026-001`、`CK-2026-001`、`XF-2026-002`、`ZX-2026-002`，流水递增无重复。

### N5【严重】编目建档留空编号直接 500（页面却提示"留空自动生成"）

**复现步骤**：进入「编目建档」→ 藏品编号留空 → 保存 → 返回「系统繁忙」；后端日志：`Field 'relic_code' doesn't have a default value`；补上编号后可保存，但随即又报 `Field 'is_public' doesn't have a default value`。

**根因**：`RelicServiceImpl.createRelic()` 只在"已传编号"时做唯一性校验，从不生成编号；`is_public` 在 `init.sql` 里写了 `DEFAULT 0`，但实际库该列无默认值（结构漂移），未传即插入失败。

**处理（已修复）**：新增 `generateRelicCode()`，前缀读系统参数 `relic_code.prefix`（当前值 `RW`），流水号按前缀最大值的 4 位递增；`is_public` 缺省补 0（保密）。**未改表结构**（遵循"不要改动数据表"的约定），改由应用层兜底。

**验证**：连续建档自动得到 `RW-0001`、`RW-0002`，同时自动生成溯源记录与二维码（内容 `https://10.19.6.8/#/scan?code=RW-0001`）。

### N6【严重】审核通过后不联动藏品库存状态，概览分布永远不变

**复现步骤**：对 TC-0001 提交「出库」单据并审核通过 → 单据状态变为"通过"，但藏品 `stock_status` 仍为 1（在库）；工作台「在库」数量不减、「出库」不增。借调、修复、注销同样如此。

**根因**：`AuditServiceImpl` 只回写业务单状态，从不修改 `relic_info.stock_status`；只有注销的"归档"动作会改藏品状态，而归档不是审核必经环节。

**处理（已修复）**

- 审核通过时联动：出入库（1 入库/3 移库 → 在库，2 出库 → 出库）、借调 → 借出、修复 → 修复中、注销 → 已注销且 `is_public=0`；**驳回不改变藏品状态**
- 反向回写补齐：借调"归还"→ 在库；修复"记录过程并填写修复后状况"→ 在库

**验证**：审核出库后 TC-0001 → 2、借调后 YX-0002 → 3、注销后 QT-0003 → 5 且公开标记为 0、修复通过后 SH-0001 → 4，概览分布随之一致变化。

### N7【中高】已审结的单据可被重复审核，结论被覆盖

**复现步骤**：某征集单审核通过（状态 2）→ 再次提交审核并选择"驳回" → 接口返回 200，单据状态变成 3，审核记录出现"通过""驳回"两条互相矛盾的留痕。

**处理（已修复）**：`doAudit` 前增加 `assertAuditable()`，按业务类型校验单据必须仍在待审核状态（征集 1 / 出入库 0 / 修复 1 / 借调 1 / 注销 0），否则返回「该单据不在待审核状态，不能重复审核」。

### N8【低】审核记录「业务类型」列为空白

**复现步骤**：审核工作台下方「审核记录」表格 → 业务类型一列全空。

**根因**：前端绑定 `bizTypeName`，`SysAuditRecordDO` 没有该字段、服务端也未翻译。

**处理（已修复）**：DO 增加 `@TableField(exist=false) bizTypeName`，`listAuditRecords` 按 `bizType` 翻译（征集审核/出入库审核/修复审核/借调审核/注销审核），顺带让 `keyword` 支持按单号与审核人检索。

### N9【中高·未修复】接口层无角色鉴权，审核员可越权读写其他模块

**涉及角色**：审核员（录入员同理）

**复现步骤**：用审核员 token 直接调用下列接口，全部返回 200 且返回完整数据：

| 接口 | 预期 | 实际 |
|---|---|---|
| `GET /relics` | 403（档案仅管理员/录入员） | 200，返回全部藏品 |
| `GET /users` | 403（系统管理仅管理员） | 200，返回用户列表（含角色、状态） |
| `GET /logs` | 403 | 200，返回全量操作日志 |
| `POST /relics` | 403 | 200，成功建档 |

**根因**：系统只在菜单与路由层按 `roleType` 隐藏入口，后端 `AuthInterceptor` 只校验 JWT 是否有效，未校验角色；目前仅审核提交/批量审核两处用了 `@RequireRole`。

**建议（未改，涉及较大范围权限矩阵，需你确认）**：给其余写接口与敏感读接口补 `@RequireRole`（征集/编目/出入库/库房/修复/借调 → 1、2；档案读 → 1、2；用户/字典/参数/日志 → 1；统计 → 1、3），前端菜单保持现状即可。

### N10【低】访问不存在的接口返回 500「系统繁忙」

**复现步骤**：`GET /api/warehouse/stock-records`（错误路径）→ `{"code":500,"message":"系统繁忙，请稍后重试"}`，后端日志为 `NoResourceFoundException`。

**处理（已修复）**：`GlobalExceptionHandler` 增加 `NoResourceFoundException` → 404、`HttpRequestMethodNotSupportedException` → 400 的映射，`ResultCode` 补 `NOT_FOUND(404)`。验证返回 `{"code":404,"message":"接口不存在：warehouse/stock-records"}`。

> 该用例同时暴露一个使用细节：出入库接口实际路径是 `/api/stock-records`（控制器未加类级前缀），前端 `api/stock.js` 与之一致，接口文档如按 `/warehouse/stock-records` 书写需修正。

### N11【低】批量通过成功提示显示"已通过 undefined 条"

**根因**：后端批量审核返回 `data=null`，前端却读取 `result.success`。

**处理（已修复）**：改为按本次提交条数提示「已通过 N 条」。

### N12【低·未修复】业务校验失败用 500 承载

**复现步骤**：驳回时不填审核意见 → `{"code":500,"message":"驳回时必须填写审核意见"}`；重复审核、单据不存在等同样返回 500。

**说明**：`BusinessException(String)` 单参构造默认沿用 `ERROR(500)`，前端提示文案正常，仅 HTTP 语义不准确。建议后续统一为 400（需全量梳理既有提示，本次未动）。

### N13【低·环境差异】`init.sql` 与实际库结构不一致

`init.sql` 中 `relic_info.is_public` / `stock_status` 声明了默认值，实际库该两列无默认值，导致不带这两个字段的插入失败（见 N5）。按"不改动数据表"的要求，本次由应用层补默认值，**建议后续用 `init.sql` 重建一次库或补 `ALTER TABLE`**，避免换环境后再次出现。

### N14【提示】操作日志已记录请求参数，含密码类字段时存在泄露风险

当前登录接口不落日志（`LoginUser` 为空直接返回），故未产生实际泄露；但新增用户、重置密码等接口的参数以 `toString` 形式入库。已在切面中增加 `password / loginPassword / token / secret` 的脱敏替换（`$1=***`），防患于未然。
